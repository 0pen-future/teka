# Frontend Guidelines

Owns: frontend feature-module contract, server/client state split, form and
validation conventions, API error handling, accessibility baseline, frontend
testing strategy.

## Module layout

```
apps/web/src/
  app/          entry, providers, router
  components/
    ui/         generated shadcn/ui primitives (regenerate, don't hand-tune)
    shared/     app-owned building blocks (theme, error boundary, page header)
  features/     one folder per domain (see feature contract below)
  layouts/      route-level shells (root, auth, dashboard)
  lib/          api client, config/env, utils — no React components
  styles/       global Tailwind/theme CSS
  test/         vitest setup, MSW handlers/server, render helpers
```

A feature folder holds `api/`, `schemas/`, `types/`, `hooks/`, `components/`,
`pages/`, `stores/`, `routes.tsx`, and `__tests__/` as needed, plus a public
`index.ts`.

Feature code depends on `components/`, `lib/`, and its own folder. Cross-feature
imports go **only** through the other feature's `index.ts` (e.g. layouts and
`users` import `useAuthStore` from `@/features/auth`) — never deep paths into
another feature's internals. `index.ts` deliberately does not export pages or
routes; `routes.tsx` is a second sanctioned entry consumed only by
`app/router.tsx`, which keeps page components out of cross-feature import
chains (avoiding circular feature imports) and leaves room for route-level
lazy loading later. Promote anything shared by multiple features
into `components/shared` or `lib`.

`components/ui/` is generated by the shadcn CLI (`components.json` holds the
config). Keep upstream shape so components can be re-generated; app-specific
lint exceptions for that folder live in `eslint.config.js`.

## Server/client state split

- **Server state** (anything fetched from the API) lives in TanStack Query —
  never copied into a store. Defaults: `staleTime` 30s, one retry, no retry on
  4xx (`ApiError.status < 500`).
- **Client state** (session, UI preferences) lives in Zustand stores under the
  owning feature (`features/auth/stores/auth-store.ts`) or React context for
  render-scoped concerns (theme).
- The access token is kept in memory only (Zustand), never in localStorage; the
  refresh token stays in an httpOnly cookie managed by the API.

## API access and error handling

All requests go through `lib/api/client.ts` (axios, `withCredentials`). The
interceptors attach the bearer token, run a single-flight refresh on 401, and
normalize every failure to `ApiError { code, message, status, fields }` —
`NETWORK_ERROR` with `status: null` when the server is unreachable. UI code
matches on `error.code`; it never inspects raw axios errors.

Environment access goes through `lib/config/env.ts` (zod-validated,
fail-fast). `VITE_*` variables are embedded in the bundle and must never hold
secrets. The dev server reads `apps/web/.env.development`; production builds
must receive `VITE_API_URL` at build time (owned by the Docker/CI setup) — a
build without it renders a readable startup error, not a working app.

## Permission gating

- Gate role-dependent nav entries and pages on the caller's effective
  permission keys via `useCenterContext().has(key)` — never on `isOwner`
  alone. The server folds the owner bypass into the `permissions` array from
  `GET /centers/me` (and `has` still short-circuits owners as rollout
  tolerance), so a plain key lookup is correct for both roles.
- A gated page needs both the hidden nav entry AND its own deep-link guard
  (redirect or enabled-gated query); hiding the link is not authorization.
  Write actions the API reserves for the owner stay behind `isOwner`.
- Permission labels come from the API catalog response only — no TS-side
  label map.

## Forms and validation

react-hook-form + zod resolvers; schemas colocated with the feature. Surface
field-level API validation errors from `ApiError.fields`.

## Accessibility baseline

Radix primitives for interactive components, `eslint-plugin-jsx-a11y` in CI,
a skip link in the root layout, `aria-label` on icon-only buttons, and both
color schemes (class-based dark mode via the theme provider).

## Testing

Two layers, two runners:

- **Unit/component tests** — Vitest + Testing Library + MSW, fully offline
  (`make test-web` / `npm run test`; `npm run test:watch` while developing).
  Files live in `src/features/*/__tests__/*.test.tsx` (vitest only picks up
  `src/**/*.test.*`; `e2e/` belongs to Playwright). `src/test/msw/handlers.ts`
  owns the happy-path API fixtures — override per test with `server.use(...)`
  for error and edge cases. `src/test/setup.ts` boots MSW with
  `onUnhandledRequest: "error"` (any unmocked request fails the test), resets
  auth state between tests, and shims jsdom gaps Radix needs (ResizeObserver,
  `scrollIntoView`, pointer capture). Render through `renderWithProviders`
  from `src/test/utils.tsx` — it wires a fresh QueryClient, theme provider,
  memory router, and toaster; `signInAs(testAdmin | testUser)` seeds the auth
  store. List pages must cover the loading/empty/error/data quartet.
- **End-to-end tests** — Playwright against a running stack
  (`make e2e` / `npm run e2e`), specs in `e2e/*.spec.ts`. Expects the app on
  localhost:5173 (override with `E2E_BASE_URL`) backed by the API with seeded
  dev users. Tests run on one worker because they mutate a shared database.
  Prefer role-based locators; use `exact: true` on cell lookups so row
  action `aria-label`s don't collide in strict mode.

## Verification

`make lint-web` runs eslint, prettier check, and `tsc -b`; `make test-web` runs
the offline unit suite; `make build-web` builds the production bundle;
`make e2e` runs Playwright against the dev stack.
