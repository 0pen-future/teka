# Phase 1: Phone Auth Rework, App Shell, Dashboard Warnings

## Overview

Convert the scaffolded email-based auth feature to phone + password, retire the
scaffolded user-management CRUD, reshape the app shell navigation around the
teacher's real workflow, and build the dashboard whose primary job is the
unattended-session alert (PRD R2 AC 3: a session already held but not yet
attended must produce a warning on the first screen).

This phase is the foundation the others mount onto: nav items, the
period-selection convention, and money/date formatting helpers land here so
phases 2–4 never invent their own.

## Requirements

- [ ] Login uses phone + password. Phone is the login identifier
      (`user_accounts.phone`, `docs/schema_design.sql:47`, `VARCHAR(20)`). The
      stored format is still open upstream — see plan open question 5.
- [ ] Register (if kept — see plan open question 4) collects full name, phone,
      password, mapping to `teachers.full_name` (`docs/schema_design.sql:66`)
      and `user_accounts.phone`.
- [ ] Session restore through the httpOnly refresh cookie keeps working
      unchanged (`apps/web/src/features/auth/components/session-restore.tsx`).
- [ ] The signed-in user object exposes `full_name` and `phone`; no `email`
      field remains anywhere in the web app.
- [ ] Profile data is read from the canonical `GET /api/v1/me`. Nothing in the
      web app calls `/auth/me`, which API plan 01 phase 3 deletes
      (`plans/260803-2244-01-api-schema-replacement-and-auth/phase-03-teacher-profile-and-scoping.md:41`).
- [ ] `apps/web/src/features/users/` is deleted along with its routes, tests, and
      nav entry — the API feature it consumes is removed in the same plan
      (`.../phase-03-teacher-profile-and-scoping.md:32`).
- [ ] Dashboard shows, above the fold, the count and list of held-but-unconfirmed
      sessions, each linking to `/sessions/:id/attendance`.
- [ ] Dashboard shows the current billing period with its status (open/closed)
      and a link into `/billing/:periodId`.
- [ ] Navigation is usable one-handed: bottom tab bar under `md`, sidebar at
      `md` and above.
- [ ] Money renders as Vietnamese đồng integers with no decimals — amounts are
      `BIGINT` đồng server-side (`docs/schema_design.sql:24`).

## Architecture

**Auth rework.** The existing feature isolates the wire contract inside
`schemas/auth-schemas.ts` and `api/auth-api.ts`, and the session lives in a
zustand store bridged into the axios interceptors
(`apps/web/src/features/auth/stores/auth-store.ts:31`). The rework is therefore
confined to the zod schemas, the two form pages, the session user shape, and
every component reading `user.email` / `user.name`.

**The users feature goes away, not phone-ified.** `apps/web/src/features/users/`
is a generic admin CRUD over `/users`
(`apps/web/src/features/users/api/users-api.ts:8-28`). API plan 01 phase 3
deletes `internal/features/users/` outright, so reworking the web mirror would
be building screens against endpoints that no longer exist. It is deleted here
instead. Five files import from it and must be repointed:
`apps/web/src/app/router.tsx:7`, `apps/web/src/test/utils.tsx:9`,
`apps/web/src/test/msw/handlers.ts:3`,
`apps/web/src/features/auth/stores/auth-store.ts:3`, and
`apps/web/src/features/auth/schemas/auth-schemas.ts:3` — that is the complete
list (`rg "features/users" apps/web/src apps/web/e2e`).

**Where the profile type lives instead.** The session user shape moves into the
auth feature as `teacherSchema` in `features/auth/schemas/auth-schemas.ts`,
consumed by `sessionSchema` in the same file. Its fields come from the canonical
profile endpoint: `id`, `phone`, `full_name`, `timezone`, `status`, `created_at`
(`plans/260803-2244-01-api-schema-replacement-and-auth/phase-03-teacher-profile-and-scoping.md:28`).
There is no `role` — V1 has one role, and plan 01 drops the `admin`/`user`
distinction. `GET /api/v1/me` is the single source for profile data;
`GET /auth/me` is removed by plan 01 phase 3 and must not be called. The web app
has never called it (`rg "auth/me" apps/web` → no hits), so this is a
forward-looking constraint, not a migration.

**Spec authority.** Write the client against the swagger regenerated by plan 01
(`make api-docs`), not the spec currently committed in `apps/api/docs` — that one
still describes email auth, the `admin` role, and `/users` paths, all of which
plan 01 removes.

**Phone normalization — one decision point, not an assumption.** Teachers type
`0912345678`. Whether the API stores and expects E.164 (`+84912345678`) or the
local `0…` form is still open upstream (plan open question 5): plan 01 phase 2
currently normalizes to E.164
(`plans/260803-2244-01-api-schema-replacement-and-auth/phase-02-phone-auth-rewrite.md:116`),
but that choice is not yet settled. Isolate it in a single exported
`normalizePhone` helper in `features/auth/schemas/auth-schemas.ts`, used by a zod
transform. The accepted *input* forms are fixed regardless of the outcome (`0…`
with 10 digits, or `+84…`); only the emitted form depends on the answer.
Switching later must mean editing one function body and its unit test — never
hunting transforms across forms. Display always uses the local `0…` form
whatever the wire format is.

**Shared formatting.** Add `apps/web/src/lib/utils/format.ts` with
`formatMoney(amountDong: number)` and `formatSessionDate(iso: string)`, both
using `Intl` with the `vi-VN` locale. Every later phase imports from here — no
local `toLocaleDateString` calls like the one currently inlined at
`apps/web/src/features/users/pages/users-page.tsx:36`.

**Period access.** Billing period ids appear in three route families
(`/billing/:periodId`, `/collections/:periodId`, `/notifications/:periodId`).
Rather than a React context, the current period comes from a shared hook
`useCurrentPeriod()` in a new `features/billing` folder created here with only
its API client, schema, and hook (pages arrive in phase 4). This keeps phase 4
from having to refactor the dashboard.

**Data flow.**

```
LoginPage --(phone, password)--> auth-api.login --> POST /auth/login
   -> sessionSchema.parse -> useAuthStore.setSession(user, accessToken)
   -> interceptors attach the Bearer token on every later request

DashboardPage -> useDashboardSummary()
   -> GET /sessions/pending        (held, attendance not confirmed)
   -> GET /billing/periods/current
   -> render PendingAttendanceAlert + PeriodStatusCard
```

**Assumed API contract** (reconcile with plans 01, 03, 04):

| Method | Path | Response payload |
|---|---|---|
| POST | `/auth/login` | `{ access_token, token_type, expires_in, user }` |
| POST | `/auth/register` | same |
| POST | `/auth/refresh` | same |
| POST | `/auth/logout` | no body |
| GET | `/me` | `{ id, phone, full_name, timezone, status, created_at }` — confirmed against plan 01 phase 3, not assumed |
| PUT | `/me` | same; accepts `full_name` and `timezone` only, phone changes rejected |
| GET | `/sessions/pending` | `[{ id, class_id, class_name, session_date, start_time }]` |
| GET | `/billing/periods/current` | `{ id, year, month, period_start, period_end, status }` |

Paths are relative to the axios `baseURL`
(`apps/web/src/lib/api/client.ts:13`), which is `VITE_API_URL` and already
carries the `/api/v1` prefix (`apps/web/.env.development:3`), so `/me` here is
`GET /api/v1/me` on the wire. There is no `/auth/me` row: that route is deleted.

tab bar, tablet `md`–`lg` 72px icon rail, desktop `lg+` full 236px sidebar.

## Risk Assessment

|---|---|---|---|
| Missed `user.email` / `user.name` reads break the build late | Medium | Low | TypeScript catches them all once `teacherSchema` replaces `userSchema`; step 7 makes the grep explicit. |
| Client phone normalization diverges from the server's, so a correct password fails | Medium | High | One `normalizePhone` owns the wire format, and the server normalizes too (`.../phase-02-phone-auth-rewrite.md:180`), so the client step is idempotent. Confirm the format against the regenerated swagger before this phase merges — plan open question 5. |
| Profile fields are read from a stale contract (`/auth/me`, `role`, email) because the committed `apps/api/docs` spec was used | Medium | Medium | Write against the swagger regenerated by plan 01; the zod parse at `parseData` fails loudly at the boundary rather than rendering blanks. |
| Deleting `features/users` removes something still referenced | Low | Low | The importer list is closed at five files (`rg "features/users"`); typecheck runs before the delete is committed. |
| Bottom nav overlaps content on short screens | Low | Medium | Reserve height with padding on `main`; verify at 375×667 during the e2e run. |
| `/sessions/pending` or `/billing/periods/current` land under different names | Medium | Low | Each is a single-function API client; renaming touches one file. |

**Rollback:** one branch touching only `apps/web`. Reverting it restores email
auth; there is no migration and no persisted client state (the access token is
