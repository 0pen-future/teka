01 · CONTRACT ĐÃ CHỐT

Bốn trường của brainstorm

Outcome

Giáo viên chọn kênh zalo_personal ở trang thông báo. Hệ thống gửi 1 tin/contact/kỳ (text sẵn có từ statements.Build) như DM từ chính tài khoản Zalo của giáo viên tới các contact đã liên kết. Ledger chuyển queued → sent/failed kèm msgId hoặc lý do lỗi. Contact chưa liên kết rơi về copy thủ công, không bao giờ lỗi.

Constraints

  • Tái dùng nền đã ship: session cache, health probe, creds mã hóa, Sender registry, statements.Build. Không refactor lại.
  • Gửi nằm ngoài DB transaction; nhịp tuần tự, gap ngẫu nhiên 3–8s, có trần mỗi run.
  • Một replica homelab; run persist trong bảng notification_runs — restart giữa run → run interrupted, teacher bấm «Gửi tiếp» để resume (không auto-resume). (Validate S1)
  • Trước khi gửi kênh personal: confirm dialog «X tự động · Y thủ công». (Validate S1)
  • Credentials không bao giờ vào log, response, git.
  • Web: TanStack Query + poll, không SSE.

Non-goals

ZNS/OA/Bot API · SMS · tin per-invoice · auto-match theo số điện thoại · chat chiều về, media, nhóm · scale đa replica.

«Nguồn gốc không có throttling. 30 tin trong 2 giây chính là chữ ký anti-spam. Nhịp gửi là tiêu chí nghiệm thu, không phải tuỳ chọn.» Guardrail kế thừa từ brainstorm 260806-1611

Acceptance criteria

  • Port send-only: SendMessage + FetchFriends, quarantine.
  • Map/unmap contact ↔ bạn Zalo qua picker, persist trên contacts.
  • Queue trong tx, run nền cập nhật từng row sent/failed.
  • Poll tiến độ x/y; đóng tab không dừng run.
  • Chưa map/hết phiên → fallback rõ ràng, không tự retry.
  • Test Go + race + web lint/build xanh.

Phase 1 · Protocol send port

phase: 1status: completedpriority: P1effort: 1ddependencies: []

Overview

Port send-only subset của Zalo personal protocol từ goclaw vào internal/features/zalo/protocol (quarantine như phần auth đã port), rồi expose 2 method mới trên zalo.Service: gửi DM và liệt kê bạn bè. Không đụng notifications ở phase này.

Requirements

  • Functional:
    • protocol.SendMessage(ctx, sess, toUID, text) (msgID string, err error): DM path only (POST {chat_service}/api/message/sms, payload {message, toid, imei, clientId, ttl}, AES-CBC encrypted params=).
    • protocol.FetchFriends(ctx, sess) ([]FriendInfo, error): decode tối thiểu userId, displayName, avatar (bỏ mọi hàm group).
    • zalo.Service.SendDM(ctx, teacherID, toUID, text) và zalo.Service.ListFriends(ctx, teacherID) dùng sessionFor (tự re-login, trả ErrNotLinked/ErrLinkExpired như hiện có).
  • Non-functional: credentials (IMEI, cookies, secret key) không bao giờ vào log/error string, tái dùng chuẩn doRequest (đã strip query string, review C-1 plan auth). Port trung thực từ source, giữ quarantine: không import protocol ra ngoài package zalo.

Architecture

  • Source port: github.com/nextlevelbuilder/goclaw@dev → internal/channels/zalo/protocol/send.go, send_helpers.go, contacts.go (DM only; drop group/typing/media/listener).
  • client.go hiện có ServiceURL, getEncryptParam, encryptParams, buildFormBody, doRequest; send port dùng lại, chỉ thêm helper còn thiếu (vd. decrypt data field của response) vào client.go/crypto.go theo ghi chú kiến trúc plan auth.
  • Session đã giữ UID, secret key, service map sau login; SendMessage chỉ nhận *Session, không đọc DB.

Related Code Files

  • Create: apps/api/internal/features/zalo/protocol/send.go (+ send_test.go)
  • Create: apps/api/internal/features/zalo/protocol/contacts.go (+ contacts_test.go)
  • Modify: protocol/{client,crypto,models}.go (chỉ khi thiếu helper; FriendInfo + envelope)
  • Modify: zalo/{service,errors}.go + service_test.go

Implementation Steps

  1. Đọc source goclaw send/contacts, xác định phần DM-only + helper thiếu.
  2. Port send + helpers (fold vào client.go nếu nhỏ), port test tương ứng (fake HTTP server như client_test/auth_test hiện có).
  3. Port FetchFriends (bỏ group), thêm FriendInfo vào models.go.
  4. Thêm SendDM/ListFriends vào zalo.Service qua sessionFor; Zalo reject session → expire + ErrLinkExpired (cùng semantics VerifyAccount).
  5. Unit test service với fake login/relogin như service_test.go hiện có.

Success Criteria

  • go test ./internal/features/zalo/... pass, kể cả -race.
  • Test chứng minh transport error không chứa IMEI/cookie (mở rộng TestFetchers_TransportErrorOmitsCredentials cho send path).
  • SendDM với session chết → account expired + ErrLinkExpired, không panic.
  • Không file nào ngoài package zalo import zalo/protocol.

Risk Assessment

  • Protocol drift: endpoint Zalo đổi bất kỳ lúc nào, không SLA. Giữ port mỏng, test bằng fake server; lỗi runtime map về failed row (phase 3), không crash.
  • Payload lệch source: so từng field với goclaw trước khi viết; không "cải tiến".

Requirements

  • Bảng notification_runs: id, teacher_id, billing_period_id, purpose, status (running/completed/interrupted/expired), created_at, finished_at; cột notifications.run_id UUID NULL FK. Counters derive bằng COUNT trên rows theo run_id — không lưu counter trùng trong bảng runs.

Architecture

  • Endpoint friends thuộc feature zalo (cần session); endpoint mapping thuộc feature contacts (chỉ ghi cột, không gọi Zalo). Không validate zalo_user_id với live friends list ở backend: picker UI là nguồn; validate live nghĩa là phụ thuộc Zalo up mỗi lần sửa contact, từ chối có chủ đích.
  • Down migration: UPDATE notifications SET channel='zalo_manual' WHERE channel='zalo_personal' trước khi restore CHECK cũ; drop run_id, drop bảng notification_runs, drop 2 cột contacts; down luôn chạy được.

Overview

Phase lõi: kênh zalo_personal trong notifications. BulkSend queue rows trong tx như cũ; sau commit, một background run gửi tuần tự qua zalo.Service.SendDM với gap ngẫu nhiên 3–8s, cập nhật từng row sent/failed. Run persist trong bảng notification_runs nên sống sót restart (Validate S1); endpoint poll + endpoint resume thủ công cho run bị gián đoạn.

Requirements

  • Constant ChannelZaloPersonal = "zalo_personal" + entry registry.
  • BulkSend với channel=zalo_personal:
    1. Pre-check: zalo.Service có session lành (linked, chưa expired); expired/chưa link → 400/409 message rõ, không ghi gì (giữ semantics «bad channel choice never leaves partial state»).
    2. Load mapping zalo_user_id cho các contact target (1 query).
    3. Contact đã map → row channel=zalo_personal, status=queued, kèm run item (notification_id, to_uid, text). Contact chưa map → row channel=zalo_manual fallback (vẫn vào BulkText copy-paste), đếm fallback_manual_count. Không bao giờ lỗi vì unmapped.
    4. Insert batch trong tx (như hiện tại); sau commit start run.
  • RunManager (in-process pacing theo mẫu LinkManager, state persist qua repo): run record tạo cùng tx với InsertBatch (status running, rows gắn run_id); 1 run active/teacher (bulk tiếp khi đang chạy → 409); goroutine gửi tuần tự (SendDM → sent + provider_msg_id, lỗi → failed + error_message; giữa 2 send ngủ rand(PaceMin..PaceMax)); xong → completed; ErrLinkExpired giữa run → mark mọi row còn lại failed («phiên Zalo hết hạn»), run expired, không tự retry; cap MaxRunSize (quá cap → 400, gợi ý gửi theo đợt); Close() dừng goroutine khi shutdown; startup reconcile: run running mồ côi → interrupted (rows giữ queued).
  • Snapshot DB-backed: run record + COUNT rows theo run_id → {run_id, period_id, purpose, status, total, sent, failed} — sống sót restart.
  • Resume thủ công (Validate S1): POST /billing-periods/:id/notifications/run/resume cho run interrupted — re-render text các row queued còn lại qua statements.Build, tiếp tục pacing trên cùng run_id. KHÔNG auto-resume lúc boot (guardrail «teacher chủ động bấm» + tránh double-send tin bay dở).
  • GET /billing-periods/:id/notifications/run → snapshot run mới nhất của period (DB-backed); không có run → {active: false}. Ledger chi tiết vẫn qua GET …/notifications hiện có.
  • Response BulkSend thêm: run_id, personal_queued_count, fallback_manual_count (schema cũ giữ nguyên cho kênh manual).
  • Config NotificationsConfig: PaceMinSeconds (3), PaceMaxSeconds (8), MaxRunSize (50); env API_NOTIFICATIONS_*, .env.example + compose cập nhật. Send ngoài tx và ngoài request goroutine; race-clean.

Architecture

  • Consumer-defined interface (mẫu StatementsSource): notifications khai báo ZaloSender { SendDM(...); Verify(...) }; *zalo.Service satisfy; container wire vào NewService. Không import cycle.
  • Sender registry vs run: Sender.Send hiện chạy trong tx nên kênh personal KHÔNG giao việc gửi cho registry; zaloPersonalSender.Send chỉ là validation no-op (như manual), orchestration nằm trong Service.BulkSend (branch theo channel) + RunManager. Doc comment giải thích ranh giới.
  • Repo mới: MarkOutcome(ctx, teacherID, id, status, providerMsgID, errMsg) (1 UPDATE/row khi đến lượt) + FailQueuedInRun(ctx, ids, reason) cho nhánh expired giữa run.
  • Run item giữ text đã render trong memory (DB không lưu message text, giữ thiết kế «never persisted»); resume re-render text từ statements.Build cho đúng các contact còn queued — không cần persist text.
  • Repo mở rộng: CRUD notification_runs (create/update status, snapshot COUNT theo run_id, reconcile running→interrupted).
  • Lifecycle: RunManager thuộc notifications.Service; container gọi Close() lúc shutdown (cùng chỗ c.Zalo.Close() trong internal/app).

  1. Config: 3 field + validate (min ≤ max, cap > 0), env mapping, defaults.
  2. Repo: MarkOutcome, FailQueuedInRun + integration tests.
  3. RunManager: struct + goroutine + snapshot + Close; unit test với fake ZaloSender, sleep hook inject được (test không ngủ thật 3–8s).

Success Criteria
